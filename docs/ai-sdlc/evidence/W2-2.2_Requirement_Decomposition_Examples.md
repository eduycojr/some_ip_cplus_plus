## Example 1: Tail Light Signaling Service Implementation (ISSUE-01)

### Stage 1: Requirement Clarification

#### Purpose
Translate ambiguous requirements into explicit acceptance criteria for Tail Light Signaling service extension (Service ID 0x1400).

#### Clarifying Questions & Approved Answers

**Q1: Tail Light Service ID and Method ID Assignment**
- **Approved Answer:** 
  - Service ID: `0x1400`
  - Method IDs:
    - Turn On: `0x0040`
    - Turn Off: `0x0050`
    - Hazard Trigger: `0x0055`
    - Query Status: `0x0060`

**Q2: Payload Binary Structure and Encoding**
- **Approved Answer:**
  - Requests: Single-byte mode parameter (0x00 = Off, 0x01 = On, 0x02 = Hazard)
  - Query Status Response: 2-byte payload
    - Byte 0: Tail light state (0x00 = Off, 0x01 = On)
    - Byte 1: Hazard state (0x00 = Inactive, 0x01 = Active)

**Q3: Port Binding and Endpoint Configuration**
- **Approved Answer:**
  - Build separate standalone binaries: `examples/taillight_server_app.cpp` and `examples/taillight_client_app.cpp`
  - taillight_server_app binds to UDP port 3004
  - taillight_client_app binds to UDP port 3006
  - Separate from Brake Control demo (ports 3000/3002)

**Q4: Hazard Light Control Semantics**
- **Approved Answer:**
  - Hazard mode is stateful (0x01 active, 0x00 inactive)
  - Turn On/Turn Off commands set the tail light state independently without clearing hazard mode
  - Hazard toggled via separate command; does not auto-cancel

**Q5: Error Handling and Fault Codes**
- **Approved Answer:**
  - Return MessageType::ERROR (0x02) for malformed request payloads or unregistered methods
  - Echo Client ID and Session ID headers in error response

| **Hazard mode independent of on/off** | MEDIUM | Approved: on/off does not affect hazard state. |

| **Backward compatibility guaranteed** | LOW | No library API changes; example apps only. |

## Example 2: UDP Request Timeout & Retry Resilience (ISSUE-02)

### Stage 1: Requirement Clarification

#### Purpose
Translate ambiguous requirements into explicit acceptance criteria for UDP socket timeout and retry mechanism.

#### Clarifying Questions & Approved Answers

**Q1: Timeout Duration — Default & Configurability**
- **Approved Answer:**
  - Default timeout: 2000 ms (2 seconds)
  - Scope: Set via configurable setter method `set_recv_timeout(uint32_t timeout_ms)` on `UdpEndpoint` and optional constructor parameter defaulting to 2000 ms
  - Unconfigured behavior: Default to 2000 ms timeout to ensure non-blocking safety

**Q2: Retry Mechanism & Scope**
- **Approved Answer:**
  - Max retry count: 3 attempts
  - Retry trigger: Socket timeout only (EAGAIN/EWOULDBLOCK/WSAETIMEDOUT)
  - Strategy: Fixed backoff delay of 100 ms between retry attempts
  - Scope: Retries handled synchronously within request sender / receive wait loop before declaring total request failure

**Q3: Error Code & Return Mechanism**
- **Approved Answer:**
  - Error Code: Return code `0x03` (ReturnCode::E_TIMEOUT / timeout error)
  - Communication: When retries exhaust, `send_to()` / receive operation returns `0x03` status with original Client ID and Session ID headers preserved

**Q4: API Signature & Backward Compatibility**
- **Approved Answer:**
  - Option B + Constructor Default: Provide setter methods `set_recv_timeout()` and `set_max_retries()`, alongside backward-compatible optional constructor arguments
  - Zero breaking changes: Existing callers compiling with default constructors receive default safety parameters (2000 ms timeout, 3 retries)

**Q5: Cross-Platform Socket Timeout Implementation**
- **Approved Answer:**
  - POSIX: Use `setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv))` with `struct timeval`
  - Windows: Use `setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO, (const char*)&ms, sizeof(ms))` with `DWORD` milliseconds under `#ifdef _WIN32`
  - Error detection: Map POSIX `EAGAIN`/`EWOULDBLOCK` and WinSock `WSAETIMEDOUT` to timeout handling

#### Silent Assumptions Audit (Forced Surfacing)

| Assumption | Risk Level | Rationale |
|---|---|---|
| **Default timeout 2000 ms** | HIGH | Safe, non-blocking value; prevents indefinite hangs. |
| **Retry count 3 attempts** | HIGH | Reasonable limit; prevents retry storms. |
| **Retry on timeout only** | MEDIUM | Other errors (ECONNREFUSED) not retried; intentional. |
| **Immediate retry + fixed 100ms backoff** | MEDIUM | Simple strategy; no exponential backoff needed. |
| **Error code 0x03 in return_code field** | MEDIUM | Consistent with SOME/IP header structure. |
| **Backward compatible defaults** | LOW | Constructor with optional params ensures compatibility. |
| **Cross-platform socket API differences** | LOW | Platform guards (`#ifdef _WIN32`) handle POSIX vs. WinSock. |

#### Testable Acceptance Criteria (Stage 1)

- ✅ PASS: Default timeout 2000 ms applied when not configured
- ✅ PASS: Custom timeout honored (setter method + constructor param)
- ✅ PASS: Retry count max 3 with 100ms backoff between attempts
- ✅ PASS: Error code 0x03 returned on final retry exhaustion
- ✅ PASS: Backward compatible: existing code compiles unchanged
- ✅ PASS: Cross-platform socket timeout behavior identical

- ❌ FAIL: Unbounded retry or infinite loop
